# v6 方案 · Discord 为主，网页做减法

> 2026-10-27 定稿，机主已确认本文的设计和第 2 节的全部决定。
> 本文取代 v5（`docs/redesign-v5/spec.md`）里所有和约局有关的设计。v5 中与约局无关的规则继续有效：判决前脱敏、段位只给本人看、CSP、深链兼容、锁定文案（第 8 节列出解除锁定的几条）。
> 实施计划：[plan-s1.md](plan-s1.md)–[plan-s5.md](plan-s5.md)。进度与交接：[HANDOFF.md](HANDOFF.md)。

## 0. 结论

- **Discord 是日常入口。** 约局整个下线（网页和机器人都删）。迟到、放鸽子改由裁判手动记一笔，机器人记录的语音进出时间作为证据。
- **网页只做三件事：**
  1. 带新人走完入户：登录 → 加入服务器并绑定 Discord → 开私信 → 名字与身份 → 机器人指南；
  2. 让人查看榜单和最近的案件；
  3. 给裁判和管理员做管理。
- **机器人新增三样：**
  1. 记录已绑定玩家进出语音频道的时间；
  2. 在一个专用文字频道里维护一条「信息板」消息，内容变化时原地编辑；
  3. 发欢迎私信，提供 `/help` 和 `/voice` 两个命令。
- **分 5 期，一期一个 PR：** S1 约局下线 → S2 入户 → S3 语音记录 → S4 信息板 → S5 管理页。

## 1. 为什么改

P3 上线后，网页的页面和入口越来越多，越做越难用。成员实际都在 Discord 里活动，Discord 才是最方便的入口。所以网页做减法：只留新人入户、看排名和案件、管理三件事，其余交给机器人。

### 3.2 入户 `/welcome`

一页纵向清单，共五步，每步一张卡。

- 每步是否完成都从服务器读，不靠浏览器存储。
- 已完成的步骤打勾并折叠，第一个没完成的步骤展开。
- 这一页同时充当「通知与身份」设置页：头像菜单里的「编辑身份」「通知与 Discord」都指到这里。

| 步 | 标题 | 完成条件 | 内容 |
|---|---|---|---|
| 1 | 登录 | `me.user` 不为空 | 「用 Nanako 账号登录」，登录后回到 `/welcome` |
| 2 | 加入服务器并绑定 Discord | `GET /api/me/discord` 的 `link` 不为空 | 先给「加入服务器」按钮（`VITE_DISCORD_INVITE_URL`），再给「绑定 Discord」按钮（现有 `/link/discord` 流程） |
| 3 | 开启私信通知 | `notify_dm` 为开，且 `dm_ok` 为真（两项 `GET /api/me/discord` 已经返回） | 私信开关；送达提示（见下）；「再发一次」 |
| 4 | 名字与身份 | `is_participant` 或 `is_judge` 至少一个为真 | 把现在 `OnboardingDialog` 的显示名和身份两块原样搬过来，裁判身份仍然只能由管理员授予 |
| 5 | 机器人怎么用 | 无（看过即可） | 指南正文（共用文案）、语音记录告知、「完成，去首页」 |

**欢迎私信：**
- 绑定成功（新绑或换绑）时，机器人发一条私信，内容是指南、信息板频道和网页地址。
- 第 3 步不追踪单条私信，只看现有的 `dm_ok`（机器人私信失败时会把它置 0）：
  - `dm_ok` 为真：「已开启。没收到欢迎私信？点「再发一次」」；
  - `dm_ok` 为假：「上次私信没送到。请确认：① 已经加入服务器；② 隐私设置里允许服务器成员私信你。改好后点「再发一次」」。
- 「再发一次」每人 24 小时内最多 3 次，只算手动重发。点了以后提示「已让机器人再发一次，去 Discord 看看；没收到就刷新本页看原因」。
- 私信开关关闭时，不发欢迎私信，也不显示「再发一次」。

**什么时候带人来这里：**
- 首次登录（`?onboarding=1`）直接进 `/welcome`。
- 绑定回跳（`?linked=discord`）也进 `/welcome`，同时显示现有的「Discord 绑定成功」提示。
- 首页上，已登录但第 2、3、4 步还没做完的人，会在待办最上面看到一张「还差 N 步完成入户 → 继续」的卡。它取代现在的「未绑定」和「私信不通」两张卡。

`OnboardingDialog` 弹窗退役。

## 5. 语音进出记录（S3）

**记什么：**
- 已绑定的人，每进一次语音频道记一段：进入时间、离开时间、频道 id、当时的频道名。
- 换频道算作上一段结束（`moved`）、新的一段开始（`moved`）。
- 静音、开关摄像头这类变化不记。
- 未绑定的人不开新段。但「离开」一律照关：不管现在是否绑定，只要这个 Discord 账号还有开着的段，就把它关掉。
- 机器人只能看到它有「查看频道」权限的语音频道。机主要保证机器人能看见所有需要留证的语音频道。

**数据**（D1 和 PG 两边建同样的表，时间都用 UTC 文本 `YYYY-MM-DD HH:MM:SS`，和 `records.created_at` 一样）：

```
voice_sessions
  id               自增主键
  user_id          text, 引用 users(id)，删用户时一起删
  discord_user_id  text
  channel_id       text
  channel_name     text
  joined_at        text
  left_at          text, 可空（为空表示还在语音里）
  start_reason     'joined' | 'moved' | 'bot_online'
  end_reason       'left' | 'moved' | 'bot_offline' | 'unlinked'，可空
  索引：(user_id, joined_at)
  唯一：同一个 discord_user_id 最多一条 left_at 为空的记录

voice_coverage                       -- 机器人在线、能看到语音事件的时段
  id               自增主键
  started_at       text
  last_seen_at     text              -- 机器人在线时每 60 秒更新一次
```

**对账（保证证据可信）：** 机器人每次拿到服务器的完整状态时都要对账一次，包括启动和断线后重新建立会话。discord.js 每次重新识别都会对本服务器触发 `GuildAvailable`，只在这个事件上对账，并且一次只跑一个。

1. 关掉所有「数据库里还开着、实际已经不在语音里」的段：`left_at` 取 `max(joined_at, 上一个覆盖时段的 last_seen_at)`，`end_reason = 'bot_offline'`。
2. 给「实际在语音里、数据库里没开着」的已绑定的人开一段：`joined_at` 取现在，`start_reason = 'bot_online'`。
3. 新开一个覆盖时段。

**覆盖时段只记真正看到了的时间：**
- 短暂断线后恢复（`ShardResume`）：静默不超过 2 次心跳（120 秒），沿用原来的覆盖时段，Discord 会补发事件；超过 120 秒，结束当前覆盖时段，从恢复时刻开新的，中间那段就成了未覆盖时段。补发事件的时间按处理时刻记，所以只是近似值。
- 记录器写库失败：停止心跳，当前覆盖时段到此为止；数据库恢复后先完整对账，再开新的覆盖时段。不能出现「显示已覆盖、其实没写进去」的情况。

**显示：**
- 按榜单时区（`RESET_TZ_OFFSET`）分日。查询按时间重叠选段：段的开始早于范围结束，并且（离开时间，或者还开着时的现在）晚于范围开始，就算在范围内。
- 每天显示首次进入时间（当天开始的段里最早的一段；当天只有从前一天延续过来的段时为空）、累计时长（跨午夜的段按天切开计算）和每一段的明细。
- 跨午夜的段在第二天也列出来，标注「接上一天」。
- `bot_online` 开始的段写「机器人上线时已在语音里」。`bot_offline` 结束的段写「之后机器人离线，离开时间不确定」。
- 查询范围里如果有不在覆盖时段内的部分，单独列出来，并写：「这段时间机器人不在线，没有记录不代表没来。」

**接口与权限：**
- `GET /api/voice?user=<id>&from=YYYY-MM-DD&to=YYYY-MM-DD`
  - 需要登录。`user` 是自己时任何人都能查；查别人要是裁判或管理员，否则返回 404。
  - 范围最多 31 天。
  - 返回分日结果加未覆盖时段，不包含任何 `discord_*` 字段。时间格式和 `records` 一样，用 UTC 文本 `YYYY-MM-DD HH:MM:SS`。
- `GET /api/voice/day?date=YYYY-MM-DD`：只给裁判和管理员，返回这一天每个人的首次进入时间和累计时长。

**保留与解绑：**
- 机器人每小时清理一次：删掉 `joined_at` 早于 `VOICE_RETENTION_DAYS`（90）天的段（开着的也删），以及 `last_seen_at` 早于这个时间的覆盖时段。
- 解绑或换绑时，旧 Discord 账号还开着的段以 `unlinked` 结束，之后不再记录这个账号。

## 6. 信息板（S4）

**放在哪：**
- 配置 `DISCORD_BOARD_CHANNEL_ID`。不填就不发信息板。
- 机器人在这个频道里只维护一条消息，存在 `discord_messages`，主键是 `('board', 'main', 'board')`。

**消息内容**（一条消息，最多 3 个 embed）：

1. **信誉榜**：上榜选手前 15 名，每行「名次. 名字 — 分数」。不显示段位，段位只给本人看。不用 @ 提及，不出现任何 Discord 账号信息。
2. **最近判决**：最近 5 起已判决的扣分案件（不算历史上的 +2 加分）。字段和排序与 `/verdicts` 相同，每条附网页链接（`webUrl` 生成的 `?case=<id>` 深链），时间用 `<t:秒:R>`。
3. **动态**：
   - 「目前有 N 起记录在处理中」：判决前的案件（`awaiting_statement`、`judging`）只给数量，不写人名，和 B1-1 一致；
   - 最新一期战报的一句话摘要加链接；
   - 「更新于 <t:秒:R>」。

按钮放在一行：「我的情况」「语音记录」「打开网页」。

**什么时候更新：**
- **触发：** 下列表变化时，PG 触发器排一个 outbox 事件 `board.refresh`。第一次变化把事件排在 10 秒后；执行前又有变化，就并进同一个事件，执行时间不往后推（`outbox_schedule` 的 coalesce 模式），所以连续不断的变化也不会把更新一直拖住。
  - `score_events` 新增；
  - `records` 新增、删除，或 `status` 变化；
  - `users` 新增、删除，或者 `username`、`display_name`、`is_participant`、`score` 变化；
  - `weekly_reports` 新增或改写。
- 机器人启动时也排一次。
- 实际延迟约 10–40 秒：事件排在 10 秒后，dispatcher 最长每 30 秒轮询一次。
- **怎么发：** 已经发过、频道也没变，就原地编辑。频道变了：删掉旧消息，在新频道发一条。消息被删了（Discord 返回 10008/10003）：重新发一条。
- 时间全部用 Discord 相对时间戳显示，所以不需要定时刷新。

## 7. 数据、迁移与计分

**约局数据：**
- 约局的表（`game_sessions`、`session_players`）和历史数据保留，因为旧案件还通过 `records.session_id` 引用着它们，但以后不再写入。
- S1 的 PG 迁移要做三件事：
  - 删除约局的触发器；
  - 删除还在排队的约局 outbox 行；
  - 为每张已发出的约局卡片排一条 `session.removed`，让机器人把旧卡片删掉。
- D1 没有 outbox 和触发器，S1 不需要 D1 迁移。

**计分：**
- 守约 +2、组局 +2 不再产生。`VIOLATIONS` 里保留这两项，用来显示历史记录。规则页和规则表只列扣分类型。
- AI 归类本来就不会给出加分类型，不用改。

**周报：**
- 新生成的周报不再统计开局数、团灭局数、组局人等约局数据。
- 旧周报照常显示：缺少这些字段或为 0 时，那几行直接不显示。

**新表：**
- S3：`voice_sessions`、`voice_coverage`。D1 和 PG 两边都建。

## 8. 规则汇总

**隐私：**
- 判决前脱敏不变。
- 分数公开，段位只给本人看。
- 网页、信息板和接口一律不暴露 `discord_*`。
- 语音记录只给裁判、管理员和本人看。

**解除的 v5 锁定**（下面这几条随约局一起删除）：
- 「单一 /约局/ 标题」；
- 409 提示「约局时间已经改了…」；
- `?session` 的跳转行为：改成落到首页并提示，参数本身仍然永久兼容。

**新增的固定文案：**
- 「约局功能已下线」；
- 「约人直接在 Discord 里喊；迟到、放鸽子由裁判记录。」；
- 「约局功能已下线，这个按钮不再有效。」；
- 「这段时间机器人不在线，没有记录不代表没来。」；
- 语音告知：「绑定后，你在本服务器语音频道的进出时间会被记录，保存 90 天，供裁判处理迟到、缺席时参考。只有裁判、管理员和你自己能看到。」（天数取自 `VOICE_RETENTION_DAYS`）。

**其他 v5 规则照旧：** CSP（不准内联样式和 `dangerouslySetInnerHTML`）、DOM 顺序就是视觉顺序、组件签名只能加可选 props、接口返回 404 时新入口静默隐藏、D1 和 PG 行为一致。
