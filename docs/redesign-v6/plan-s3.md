> v6 第 3 期。方案见 [spec.md](spec.md) §3.4、§4.1、§4.4、§5、§8。前提：S1、S2 已合并。

## 1. 目标

- **机器人**：已绑定的人每进一次语音频道，就在 `voice_sessions` 记一段。机器人每次拿到服务器的完整状态都要对账一次。机器人在线、确实看得到语音事件的时段记在 `voice_coverage`。记录保留 90 天。
- **网页 `/admin/voice`**：裁判和管理员能看两样东西：
  - 某一天有哪些人进过语音；
  - 某个人最近 7、14 或 31 天的分日明细，以及其中的未覆盖时段。
- **机器人 `/voice [days] [user]`**：任何人都能看自己的记录；裁判和管理员可以指定看别人。
- **记一笔**：选好当事人后，多一个「看 TA 的语音记录」链接。
- **告知**：指南、入户第 5 步、规则页都写明「会记录语音进出」。

不在 S3：`/admin/ai`、`/admin/members`（这两页在 S5）。

### 3.2 表

两边的表结构相同。时间都存 UTC 文本 `YYYY-MM-DD HH:MM:SS`，由写入方显式给值，表上不设默认值。PG 写入时用 `datetime('now')`，0001 里定义过这个函数。所有建表、建索引语句都带 `IF NOT EXISTS`，重复执行不会报错。

**PG：`server/migrations/0010_voice.sql`**

```sql
CREATE TABLE IF NOT EXISTS voice_sessions (
  id              bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  user_id         text NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  discord_user_id text NOT NULL,
  channel_id      text NOT NULL,
  channel_name    text NOT NULL,
  joined_at       text NOT NULL,
  left_at         text,
  start_reason    text NOT NULL CHECK (start_reason IN ('joined', 'moved', 'bot_online')),
  end_reason      text CHECK (end_reason IN ('left', 'moved', 'bot_offline', 'unlinked')),
  CHECK ((left_at IS NULL) = (end_reason IS NULL)),
  CHECK (left_at IS NULL OR left_at >= joined_at)
);
CREATE INDEX IF NOT EXISTS voice_sessions_user_joined ON voice_sessions (user_id, joined_at);
CREATE UNIQUE INDEX IF NOT EXISTS voice_sessions_one_open ON voice_sessions (discord_user_id) WHERE left_at IS NULL;

CREATE TABLE IF NOT EXISTS voice_coverage (
  id           bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  started_at   text NOT NULL,
  last_seen_at text NOT NULL,
  CHECK (last_seen_at >= started_at)
);
CREATE INDEX IF NOT EXISTS voice_coverage_seen ON voice_coverage (last_seen_at);
```

**D1**：
- 新增 `migrations/005_voice.sql`，自增主键写 `INTEGER PRIMARY KEY AUTOINCREMENT`。SQLite 也支持带 `WHERE` 的部分唯一索引。
- 同样的表加进 `schema.sql`。
- `package.json` 里照 `004` 的写法加 `db:migrate5:local` 和 `db:migrate5:remote`。

D1 环境没有机器人，表永远是空的，接口照常返回，结果全是未覆盖时段。

**测试清表**：`voice_sessions` 和 `voice_coverage` 两张表都要加进 `tests/pg/setup.ts` 和 `tests/worker/setup.ts` 的 `TABLES` 列表。`voice_coverage` 没有外键，`TRUNCATE users CASCADE` 清不到它。

### 第 1 步 · 分日计算（纯函数）

新增 `shared/voiceDays.ts`：

```ts
export interface VoiceSegmentRow { channel_name: string; joined_at: string; left_at: string | null;
  start_reason: VoiceStartReason; end_reason: VoiceEndReason | null }
export interface CoverageRow { started_at: string; last_seen_at: string }
export interface VoiceDaySegment extends VoiceSegmentRow { continued: boolean }   // continued：接上一天
export interface VoiceDay { date: string; first_join: string | null; total_min: number; segments: VoiceDaySegment[] }
export interface VoiceGap { from: string; to: string }
export function voiceRangeBounds(from: string, to: string, offsetHours: number): { start: string; end: string };
export function voiceDays(input: { segments: VoiceSegmentRow[]; coverage: CoverageRow[]; from: string; to: string;
  offsetHours: number; now: string }): { days: VoiceDay[]; gaps: VoiceGap[] }
```

**规则：**

- **范围**：`from` 和 `to` 是榜单时区的日期，两端都包含。`voiceRangeBounds` 把它们换算成 UTC 的 `[start, end)`，查询和计算都用它。范围里的每一天都要输出，没有记录的天，`segments` 为空数组。
- **跨午夜的段**：在它覆盖到的每一天都出现，各天只累计落在当天的分钟数。某一天里，`joined_at` 早于这一天开始时刻的段，标 `continued: true`，页面上显示「接上一天」。查询范围开始之前就已经进去的段也是这样。
- **`first_join`**：当天开始的段里最早的 `joined_at`。如果当天只有接上一天的段，就是 `null`。
- **还开着的段**（`left_at` 为空）：按 `now` 计算时长。
- **未覆盖时段**：
  1. 从 [`start`, `min(end, now)`] 中减去所有 [`started_at`, `last_seen_at`]，剩下的部分就是未覆盖时段。
  2. 例外：如果最新一条覆盖时段的 `last_seen_at` 距 `now` 不超过 2 × 心跳，把它的结束时刻视为 `now`。
- **时间格式**：所有输入输出都是 UTC 文本 `YYYY-MM-DD HH:MM:SS`，和 `records` 一致。前端按现有的方式解析和显示。

**测试（unit）：**
- 一段跨午夜：两天都出现，第二天 `continued: true`，第二天的 `first_join` 为 `null`；
- 一段还开着；
- 一天内有多段；
- +8 时区的日界；
- 没有任何覆盖时段：整个范围都是未覆盖；
- 覆盖时段中间断了一截；
- 最新的覆盖时段被视为延续到现在。

### 第 2 步 · 记录器决策（纯函数）

新增 `server/src/voice/plan.ts`：

```ts
export type VoiceAction =
  | { kind: 'open'; discordUserId: string; channelId: string; channelName: string; reason: VoiceStartReason }
  | { kind: 'close'; discordUserId: string; reason: VoiceEndReason };
/** 一次 voiceStateUpdate。频道没变（静音、摄像头等）时返回 []。 */
export function planVoiceUpdate(prev: { channelId: string | null }, next: { channelId: string | null; channelName: string | null },
  discordUserId: string, bound: boolean): VoiceAction[];
/** 拿到完整状态时对账。open：数据库里开着的段；present：现在在语音里的人。 */
export function planReconcile(open: { discordUserId: string; channelId: string }[],
  present: { discordUserId: string; channelId: string; channelName: string }[], bound: ReadonlySet<string>): VoiceAction[];
```

**规则：**

`planVoiceUpdate`：

| 情况 | 产生的动作 |
|---|---|
| 离开（`next.channelId` 为空） | 一个 `close`，原因 `left`。**不看是否绑定**，开着的段一定要关。 |
| 进入 | 只在已绑定时产生一个 `open`，原因 `joined`。 |
| 换频道 | 一个 `close`（原因 `moved`，不看是否绑定），已绑定时再加一个 `open`（原因 `moved`）。 |

频道名为空时，用 `VOICE_UNKNOWN_CHANNEL`。

`planReconcile`：
- 数据库里开着、但人已经不在，或者已经不在那个频道的段，产生 `close`，原因 `bot_offline`。
- 人在语音里、已绑定、但没有开着的段（包括刚换了频道的），产生 `open`，原因 `bot_online`。

**测试（unit）：**
- 每种情况各一条；
- 静音不产生动作；
- 未绑定的人离开时仍会产生 `close`；
- 未绑定的人进入时不产生 `open`。

### 第 3 步 · 迁移与记录器

1. 迁移按 3.2 写。
2. 新增 `server/src/voice/recorder.ts`，直接用 `pg.Pool` 读写，和 dispatcher 的做法一样。

   **按人排队**

   同一个 Discord 用户的所有工作，排进一条 Promise 链依次执行：查绑定、写库、对账产生的动作都算在内。这样先离开、后进入的顺序不会被写反。

   **写库动作**

   - 入口是 `recorder.onVoiceUpdate({ discordUserId, prevChannelId, nextChannelId, nextChannelName })`。它把整件事排进这个人的队列；轮到时先查 `discord_links` 得出 `bound` 和 `user_id`，再调用 `planVoiceUpdate`，然后执行算出的动作。调用方不预先算 `bound`。
   - `open`：用队列里查到的 `user_id` 执行 `INSERT … ON CONFLICT DO NOTHING`，由部分唯一索引挡住重复。查不到绑定就不会产生 `open`。
   - `close`：
     ```sql
     UPDATE voice_sessions
        SET left_at = datetime('now'), end_reason = $reason
      WHERE discord_user_id = $1 AND left_at IS NULL
     ```

   **对账（`reconcile`）**

   - 一次只跑一个。上一个没跑完，新来的请求合并成「跑完再跑一次」。
   - 跑之前，先读一次当前缓存，交给 `planReconcile` 算出动作。动作按人进各自的队列；执行的时候再核对一次缓存，人已经走了的，就不再开段。
   - 以 `bot_offline` 关段时，`left_at = max(joined_at, 上一条覆盖时段的 last_seen_at)`。没有上一条覆盖时段时，取 `joined_at`。
   - 全部动作写完以后，插入一条新的覆盖时段，`started_at` 和 `last_seen_at` 都取当前时间。

   **心跳**

   每 `VOICE_HEARTBEAT_MS` 执行一次。只有同时满足下面三个条件，才更新当前覆盖时段的 `last_seen_at`：
   - gateway 处于 `ready`；
   - 有当前覆盖时段；
   - 记录器没有处于「降级」状态。

   **降级**

   任何一次写库失败，都会进入降级：打日志，并丢掉「当前覆盖时段」，这样它的 `last_seen_at` 就停在出错之前。之后每次心跳都试一次对账，对账成功后退出降级。宁可显示未覆盖，也不能「显示已覆盖、其实没写进去」。

   **断线恢复（`ShardResume`）**

   如果距离上次心跳超过 2 × `VOICE_HEARTBEAT_MS`，就丢掉当前覆盖时段，从此刻起开一条新的。不对账：Discord 会补发断线期间的事件。补发事件的时间按处理时刻记，只是近似值。

   **清理**

   每小时执行一次：
   - 删除 `joined_at` 早于 `VOICE_RETENTION_DAYS` 天的段，开着的也删；
   - 删除 `last_seen_at` 早于这个时间点的覆盖时段。

3. `server/src/discord/links.ts`：在下面两处的同一批语句里，各加一条 `UPDATE`，把旧 Discord 账号开着的段以 `unlinked` 关掉：
   - `unlinkAccounts`；
   - `linkAccounts` 的换绑分支，也就是删除旧绑定的那段。
4. **测试（pg）：**
   - 进入后离开：一段，原因分别是 `joined` 和 `left`；
   - 换频道：两段，原因都是 `moved`；
   - 同一个人并发写：只有一段开着；
   - 未绑定的人进入：不写；
   - 绑定后进入、解绑、再离开：这一段被解绑关掉（原因 `unlinked`），之后的离开不报错；
   - 对账 A：先插一条开着的段（`joined_at` 为 20 分钟前），再插一条覆盖时段（`last_seen_at` 为 10 分钟前）。对账后，这一段以 `bot_offline` 关掉，`left_at` 等于那个 `last_seen_at`，并且新增了一条覆盖时段；
   - 对账 B：开着的段的 `joined_at` 晚于上一次的 `last_seen_at`。关段后 `left_at` 等于 `joined_at`，没有负时长；
   - 降级：模拟一次写库失败后，心跳不再更新 `last_seen_at`，下一次对账成功后才开新的覆盖时段；
   - 清理：91 天前的段（开着和关着的都算）被删掉，昨天的段还在；
   - 换绑：旧账号开着的段以 `unlinked` 结束。

### 第 4 步 · 接上机器人

2. **intents 和缓存**：

   - `makeCache` 删掉 `VoiceStateManager: 0`；

3. **`wireVoice` 挂的事件**：

   | 事件 | 处理 |
   |---|---|
   | `Events.VoiceStateUpdate` | 只处理 `guildId` 这个服务器。把原始的前后频道交给 `recorder.onVoiceUpdate`，绑定的查询和 `planVoiceUpdate` 都在 recorder 的队列里做。不要去判断 `member?.user.bot`：成员缓存是空的，这个判断永远不会生效；机器人账号本来也绑不了。 |

### 第 5 步 · 读取接口

1. **新增 `worker/voice.ts`**，走 D1 接口，D1 和 PG 两边都能跑。查询一律按时间重叠选段：

   ```sql
   joined_at < :end AND COALESCE(left_at, :now) > :start
   ```

   - `getVoiceHistory(db, userId, from, to, offsetHours, now)`：读出这些段和覆盖时段，交给 `voiceDays`。
   - `getVoiceDay(db, date, offsetHours, now)`：返回当天每个人的 `{ user: UserRef, first_join, total_min, in_voice_now }`，按 `first_join` 排序，`null` 排最后。在前一天就已经在语音里的人也要算进去。
2. **`worker/routes.ts`**：
   - `GET /api/voice?user=&from=&to=`
     - 要求登录，未登录照现有写法返回 401；
     - `user` 必填；
     - `user` 不是自己时，调用者必须是裁判或管理员，否则返回 404；
     - `from`、`to` 默认最近 7 天；格式不对或跨度超过 31 天，返回 400；
     - 返回 `{ user: UserRef, days, gaps, retention_days }`。
   - `GET /api/voice/day?date=`：只有裁判和管理员能查，其他人返回 404。`date` 默认取今天（榜单时区）。
   - 两个接口的返回里都不能有 `discord_*` 和 `channel_id`。
3. **测试（worker，D1；pg 套件会在 PG 上再跑一遍）**：
   - 本人可以看自己的记录；
   - 普通人看别人返回 404；
   - 裁判看别人返回 200；
   - 未登录返回 401；
   - 跨度 32 天返回 400；
   - 返回体里没有 `discord`；
   - 空表时整个范围都是未覆盖；
   - 前一天 23:30 进、当天 00:30 离开的人，出现在当天的 `getVoiceDay` 里，`first_join` 为 `null`，`total_min` 为 30。

## 5. 不能破的约束

- 只记已绑定的人；离开事件不管是否绑定，一律照关。
- 接口、网页、机器人回复里都不能出现 Discord id 或频道 id。
- 普通人不能看别人的记录。拒绝时返回 404，不是 403，以免暴露这一页的存在。
- 未覆盖时段必须显示出来，不能用「无记录」糊过去；降级期间不能续覆盖时段。
- CSP：不写内联样式。
