**核心改动**
1. **首屏「要你处理」**：一个列表收齐所有角色的待办，包括新邀请、改时间、快开局的约定、待写说明、待点名、待确认升级、待复核申诉、取消通知和设置提示。邀请卡上可以直接回复，一下就完成。

## 1. 设计目标与原则

### 1.1 目标（按优先级）

1. **从 Discord 私信点进来的人，两下以内做完要做的事**：回复邀请、写说明、去点名、申诉、复核。
2. **组织者在网页上能完整组一局**：创建、再叫人、改时间、取消、分享、点名、结算、再约一次。`/yue` 回复里那句「在网页上可以看到它、邀请人」（`server/src/discord/sessions.ts:276`）要成真。
3. **新朋友和访客看得懂、进得来**：分享链接 → 看到这一局 → 登录 → 回到这一局。
4. **罚要有出路，梗要有出处**：低分、被立案、判决这些地方放软语气；约局、空状态、庆祝照常玩梗。
5. **一个人业余也维护得动**：小 PR、可回滚；D1 和 PG 两套引擎的迁移尽量少；不加重依赖。

### 1.2 原则

1. **首屏回答「我现在要做什么」**：所有角色的待办都在「要你处理」里，排在战报前面（CONTRACT.md:406-407）。
2. **URL 就是视图**：链接里只放 id；返回键关的是当前层；旧链接永久有效；链接本身从不写数据（「A link never writes」）。
3. **一件事只有一份数据，只有一处操作**：
   - 同一局的回复按钮在一个页面上只出现一处（`session-rsvp-moved.test.tsx:77,87`）。
   - 各处共用同一份数据；操作后有 toast 反馈；能撤销的地方给撤销。
4. **网页不比 Discord 宽松**：
   - 段位只在本人视图显示（bot 查别人时只给分数：`server/src/discord/commands.ts:211-216`）。
   - 申诉理由可以不填（和 bot 的「申诉理由（可不填）」一致，`case-actions.ts:120-122`），上限两边都是 `APPEAL_MAX` = 500。
   - RSVP 统一叫「来 / 待定 / 不来」，bot 同步改。
   - 用词以用词表（§5）为准。唯一有意保留的差异是「说明」和「陈述」：网页叫「说明」，Discord 叫「陈述」，用词表里注明两者是同一件事（§11 第 15 条可推翻）。
5. **只写事实，不承诺做不到的事**：
   - 回血：周一 0 点（看板时区）之后，第一次有人打开网页（`GET /api/config`）或定时任务触发时执行，所有在榜且不满 100 的人统一 +15，最多回到 100（`worker/routes.ts:210-229`、`worker/db.ts:410,430-432`）。对用户仍说「周一 0 点回血」，但倒计时一律读 `config.nextResetAt`。
   - 不写「他们会收到私信」，写「绑了 Discord、开着私信的人会收到」。
   - 后端没有限制的事，不承诺「只能一次」。
   - 后端没有的进度，不画进度条（见 §3.10 的立案等待提示）。
6. **手机优先**：1–1.5 屏内看到待办、自己的分数和前几名；分数在任何宽度下都看得到；长内容用页面，不用弹层。
7. **默认有安全网**：危险操作要确认；长文本存草稿；出错只影响那一块。
8. **底座克制**：手写路由，不加依赖；遵守 CSP；DOM 顺序就是视觉顺序（`App.tsx:298-307` 的注释），不用 CSS `order`。
9. **常量只从 `shared/` 读**：前端、Worker、bot 用到的同一个数字只定义一次（P0-5、P2-4 完成迁移）。

**子页导航不是 tablist**：`/board` 的 4 个子页和 `/admin?tab=` 都是路由链接，渲染成 `<nav aria-label="…">` 里的 `<Link>`，当前项加 `aria-current="page"`，不用 `role="tab"`。这样每个子页都有自己的地址，也顺手解决了「tablist 只实现了一半」。

**路由规则**（`src/lib/router.ts`[新]，手写约 80 行，提供 `useRoute`、`navigate`、`<Link>`，监听 popstate）：

- **数字 id** 只接受 `^[1-9]\d{0,14}$`，复用 `src/lib/deepLink.ts:12` 的 `ID` 正则（要先把它导出）。
- **用户 id**（`/players/:id`）来自 OAuth subject，格式不受约束（`worker/oauth.ts:90`）。只要求非空、不超过 128 字符、不含 NUL，使用时一律 `encodeURIComponent`。
- **不用 hash 做路由或锚点**：路由忽略只改了 hash 的 popstate；页内跳转用按钮加 `scrollIntoView`。
- **路由自己推入的每一条历史都带标记**：`history.state = {edg: 1, …}`。
- **直接打开深层地址时垫一条 `/`，只垫一次**：只有在 `history.state?.edg !== 1`（新开的标签页、从外部链接或书签进来）并且路径不是 `/` 时，才先 `replaceState({edg:1}, '', '/')`，再 `pushState({edg:1}, '', 原地址)`。在 `/sessions/5` 上刷新时 `history.state` 还在，不会再垫，历史栈不会越刷越长。
- **浮层**（底部抽屉、确认层）：打开时 `pushState({edg:1, sheet: <名字>})`；界面上的关闭按钮调用 `history.back()`；popstate 时只关栈顶那一层。
- **刷新后不恢复浮层**：启动时如果 `history.state.sheet` 存在，就 `replaceState` 去掉它，浮层不重开。代价是之后按一次返回，页面看起来没变（回到同一地址的无浮层条目），可以接受。
- **两个 id 对不上时**：`/players/A/cases/7` 里，如果第 7 起的 `record.subject.id` 不是 A，以 `record.subject.id` 为准，`replaceState` 到正确的选手地址，不报错。
- **找不到时**：
  - `/cases/:id`、`/players/:id/cases/:caseId` 返回 404：沿用原文案「链接里的案件不存在了。」（500 时用「打不开链接里的案件，稍后再试。」），附「回大厅」。
  - `/sessions/:id` 返回 404：「找不到这局，链接可能写错了。」附「回大厅」「看约局历史」。被取消的局不会 404，照常显示灰色的已取消状态。
  - `/players/:id` 返回 404：「找不到这位选手。」附「看信誉榜」。

### 2.3 旧深链映射（永久兼容）

启动时由 `readDeepLink` 读一次参数，只消费自己认识的参数，其他参数（比如 `utm`）原样保留。首次登录引导的优先级高于深链：先把目标存在内存里，等引导关掉再跳转，语义和现在的 `onboardingAsked` 一致。

4. 回跳记录读一次就删。新增 `tests/dom/login-return.test.tsx`，断言整个回跳过程**没有任何 POST**。

### 4.3 「组织者知道谁收不到通知」（M22）的处理

**不做「N 人里 M 人能收到私信」这个数字。** 即使设了总数门槛，组织者每次只加一个人、对比前后的数字，也能推出某个人有没有绑 Discord。改用三种不涉及隐私的做法：

1. **文案说实话**：InviteSheet 写清楚「绑了 Discord 且开着私信的人会收到；同一个人一天最多收到你 3 条邀请私信」（`dispatcher.ts:80`）；发完邀请的 toast 提醒「在群里喊一声」。
2. **让本人知道自己收不收得到**：dm_ok=0 时，本人的收件箱置顶提示，并且在 `/me/notify` 提供「我改好了」重试。
3. **分享兜底**：控制台和成功卡上都有「复制邀请链接」。

   - 地址从 `VITE_DISCORD_INVITE_URL` 读，不写死；没配置时整行隐藏。推荐填 `https://discord.nanako.org`：它是 Node 端的分享页（`compose.yaml:81-87`），没配 `INVITE_CODE` 时会自己生成会轮换的 instant invite。不要直接填 discord.gg 的邀请码，否则邀请码一轮换，网页上的链接就失效了。
2. **Discord 绑定**：
   - 入口从「编辑我的身份」的深处挪到 `/me/notify` 第 ② 步，另外 `/join` 第 ④ 步也有。
   - 文案讲清好处：「被约、改时间、该写说明都会私信你，在私信里能一键报名」。
   - 没绑的人在收件箱末尾看到一条可关闭的提示。
   - **先去绑定不会丢掉还没保存的身份选择**（M21 后半，P0-5）：`DiscordLinkCard.tsx:120-122` 的绑定是顶层跳转。在 OnboardingDialog 里点「绑定 Discord」时（不拦截跳转，只在 onClick 里），先把当前选择写进 `sessionStorage['edg.draft.onboarding']`；绑定回来、引导再次打开时（`App.tsx:198-208`），用草稿代替 `initialChoice` 预选，用户仍要点保存才写入。不增加任何请求；没有草稿时行为和现在一样。
3. **新人上榜**：
   - 首登引导讲清后果：「上榜后，你的分数会公开在榜上，答应了却没来会被记一笔。也可以先看看，以后在『我的』里随时上榜。」
   - **「先看看」只给首次登录、从来没有身份的用户**（`is_participant=0 && is_judge=0`）。它是首登对话框里的第 4 个选项，保存为两个身份都是 false。这类用户不预选任何选项。
   - 「先看看」卡片的说明里**不再写**「裁判资格由管理员授予」：`onboarding-roles.test.tsx:42` 要求这句正好出现 2 次。
   - 选「先看看」不触发任何额外请求（保存走现有的 `/api/me/roles`）。
   - 已上榜的人不受影响：仍按现有的 `initialChoice` 预选，`onboarding-roles.test` 不用改。
   - 选了「先看看」后，在 localStorage 记 `edg.onboarded.<userId>`。这样绑定 Discord 回来时（`App.tsx:198-208`），不会因为「两个身份都没有」再弹一次首登引导。没选过「先看看」的人保持现有行为，`discord-link.test:267` 照常通过。
   - **防止下榜躲罚**：现在 `/api/me/roles` 允许任何人随时把 `is_participant` 改成 false（`worker/routes.ts:327-341`），而下了榜的人不能被立案（`worker/case-filing.ts:91 requireParticipant`）。后端要加一条规则（§8 B4-4）：非管理员把 1 改成 0 时，如果名下有未结案件（待说明、裁决中、申诉中），或者 14 天内有已判决的扣分，就返回 409「你有未结束或最近的记录，暂时不能下榜，需要的话找管理员」。
4. **不在榜的朋友**：
   - 可以被邀请，名单里标「未上榜，不参与计分」。
   - 点名时他们只记出勤，不生成记分草稿（后端现有规则）。
5. **分享链接**：分享就是邀请。见 §4.1 第 ⑪ 步、登录回跳、`/join`。
6. **「谁拉你来的」（invited_by）**：**不做**。它需要签名 token 和新列，收益小，还多一个隐私面。

- **Toast**（`Toast` + `useUndo`[新]）：
  - `role=status`，`aria-live=polite`。

  - toast 里的撤销都有其他入口（比如回复随时能改），不依赖时限（WCAG 2.2.1）。
- **触控与 hover**：hover 样式包在 `@media (hover:hover)` 里；断点统一为 600 和 1024 两档。

## 10. 风险与取舍

1. **计分板退出首屏的中心位置。**
   - 想来看热闹的人要多点一下「信誉榜」。红黑榜和「头号鸽王」这种梗的主舞台没有了，群里可能有人觉得网页变正经了。
   - 补偿：梗留在约局、空状态、庆祝和战报正文里；榜单前 5 名仍在首页 1.5 屏内。
2. **约局少的时候大厅会显得冷清。** 某周只有 0–1 局时，首页只剩收件箱、空状态和榜单。缓解：空状态引导组局，榜单和战报兜底。
3. **公开段位变成只显示分数，但这是语气上的约定，不是保密。**
   - 别人看不到「资深鸽王」这类称号了，这和 bot 一致，但会损失一部分玩笑。
   - 段位完全由公开的分数决定（`tierFor`），`/api/config` 也公开返回完整的 `tiers`，规则页仍列出区间。任何人都能从分数反推出段位。所以「段位只给本人看」只是**展示层**不主动给别人贴标签，算不上隐私保护。拍板 §11 第 4 条时请按这个理解。
   - 如果要恢复公开段位，就是换回一个 chip，但必须先拍板，并和 bot 保持一致。
4. **收件箱在 P4 之前靠前端拼装，不完全准确。** 待确认升级只看 feed 前 50 条；本周之星在 feed 不够一整周时直接隐藏；可撤案卡片 P4 之前不进收件箱。登录后首屏会多 1–2 个请求，跨站延迟下会多一个 RTT，用骨架屏和逐块出现来缓解。
5. **路由带来新的维护面**：返回键、浮层入栈、直接打开深层地址时垫一条 `/`、滚动恢复、iOS Safari 和 Android Chrome 的差异。P1-5 专门留了实机验收时间。所有托管都要配好 SPA 回退，dist 里永远不能有 404.html。
6. **D1 Worker 和 Node 两套后端的能力会进一步分叉。** B2-5、B5-5 只在 Node 端实现；D1 上本来就没有私信。每个新入口都必须在接口返回 404 时静默隐藏，并配降级测试。
7. **改期变顺手以后可能被更频繁地使用。** 每次改期都会重置所有人的回复，私信 3 分钟内合并，但每人每天的额度是 10 条。缓解：确认文案写明影响人数；不提供「静默改期」。
8. **取消不能撤回。** 为了不出现「看起来取消了、其实没取消」，选择确认后立即提交。代价是手滑只能重建一局（会再发一轮邀请私信）。所以取消按钮放在最后、做成次要按钮，并且要二次确认。
9. **下榜保护会给少数正当下榜的人添麻烦**：有未结案件时要找管理员。这是为了堵住「下了榜就不能被立案」的漏洞（`case-filing.ts:91`）。
10. **组织者看不到可达人数。** 为了不暴露谁绑了 Discord，只能靠诚实的文案、本人自查和「发到群里」兜底。
11. **改分不留理由（M8 的一部分）是有意的。** 分析 §7 把「history 和改分记录带上 reason」列为需要的接口；本方案只显示「管理员调整」。原因：`score_events.reason` 只存机器码，战报和 `week_delta` 都靠它过滤（`reason NOT IN ('weekly_heal','admin_adjust')`），往里写自由文本会让数字算错；另开一列存理由又多一处隐私面，对 1–2 个管理员的小群收益不大。
12. **判决前脱敏到「只说有一起记录」会少一点透明度。** 无关的人在判决前看不到类型和区间，只知道有人有一起记录在处理中。好处是不做有罪推定；代价是前端要处理 `type` 为 null 的记录，B1-1 多约 0.5 人日。可以按 §11 第 3 条退回只隐藏 claim。
13. **有意改动的契约、文案和测试**（都已标出替代方案）：
    - CONTRACT 的深链措辞改为「翻译成视图地址」；
    - record-privacy：现有用例不改，**新增**判决前脱敏的用例；
    - bot：RSVP 标签、`/yue` 权限、`/score` 本人说明三处源码改动，都是**新增**断言（现有测试没有锁这些）；
    - 后端申诉理由上限从 1000 降到 500（和 bot 一致）；
    - 网页文案：「裁判陈述」改「立案经过」，「待陈述」改「待说明」，战报奖项改「上周之星 / 上周鸽王」；
    - 周报口径改为按判决时间；
    - CSP 收紧时新增断言；
    - 组件签名一个不改，只加可选 props。
14. **工作量比草案多了约 10 人日。** 主要来自视觉系统各项落到 PR、常量迁移、Modal page 语义、实机验收和几项低估。如果要压回 30 人日左右，按 §11 第 11 条的瘦身选项砍。
15. **不做**：
    - 浅色模式、service worker、每个约局一张 OG 预览、webcal、invited_by；
    - walk-in、连胜、请假、延期、报名留言；
    - 「有人退出 / 人齐了」主动提醒组织者；
    - 组织者可达人数；
    - 立案逐人进度；
    - 一键退出所有设备；
    - 「记一笔」支持加分（低优先级，留到以后）。
